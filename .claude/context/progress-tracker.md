## Completed

- **Bug 1 — markdown not parsed (tables and every other element type)** — THREE separate causes, all now fixed and verified against a real `Editor` instance in `tests/markdown-editor.test.ts` (jsdom), using the exact table the user reported:
  1. **Blank lines between table rows.** The reported paste had every row separated by a blank line. A blank line terminates a table per GFM, so `marked`/`markdown-it` both parse it as a stack of pipe-filled paragraphs — and `@tiptap/extension-table`'s own `markdownTokenizer` explicitly cuts its candidate at `src.indexOf("\n\n")`, so it can't help either. `normalizeMarkdownSource()` (`lib/tiptap/markdown-signal.ts`) drops blank runs that sit BETWEEN two pipe rows and leaves every other blank line alone.
  2. **Double-parsing.** The first attempt called `parser.parse(md)` and handed the resulting HTML to `setContent`/`insertContent` — but `tiptap-markdown` overrides both commands to run `parser.parse()` themselves, and its `insertContentAt` override forces `{ inline: true }`, whose `normalizeInline` unwraps block structure. So the pre-parsed HTML got run through markdown-it a second time and came out flattened.
  3. **Wrong package.** Migrated off `tiptap-markdown@0.9.0` (community, markdown-it, HTML-string output, paste hook that only fires when the clipboard has no html flavour) to the OFFICIAL **`@tiptap/markdown@3.30.1`** — version-matched to our Tiptap 3.30, `marked`-based, and it returns ProseMirror JSON rather than an HTML string, so the double-parse trap doesn't exist. Parsing is now opt-in per call via `contentType: "markdown"`. `@tiptap/extension-table`/`-bold`/`-italic`/`-strike`/`-code`/`-link`/`-list`/`-horizontal-rule` all already ship `parseMarkdown`/`renderMarkdown` specs, so every element type maps without extra work, and `editor.getMarkdown()` now serializes back out. `tiptap-markdown` uninstalled.
- **Bug 1 (cont.) — what else changed:** `use-canvas-paste.ts`'s `textToMarkdownDoc` turned a pasted markdown string into one plain paragraph per line — no parsing at all, so a paste that landed on the canvas (rather than inside an already-open note) could never produce a table no matter what the editor supported. Pasted text is now handed to the new note as `{ pendingMarkdown: text }` (mirroring bookmark's `pendingUrl`) and `MarkdownWidget` consumes it on mount via `setContent(normalizeMarkdownSource(md), { contentType: "markdown" })` — parsing has to happen there because the widget's own extension set decides which nodes the markdown may produce. Also broadened the paste detector: the old `MARKDOWN_SIGNAL` only matched headings/fences/table rows, so pasted bold/italic/strikethrough/lists/links/task-lists/inline-code fell through to the raw-text path. Detection lives in `lib/tiptap/markdown-signal.ts` (`shouldParseAsMarkdown`, `looksLikeMarkdown`, `normalizeMarkdownSource`), unit-tested in `tests/markdown-signal.test.ts`. Rule for competing clipboard flavours: if `text/html` carries real formatting tags, ProseMirror's html path wins; if its only "rich" tag is a `<pre>`/`<code>` wrapper (the usual shape when copying a markdown code block out of a chat/docs page), the plain-text flavour is parsed as markdown instead. `markedOptions: { gfm: true, breaks: true }` in both editors keeps a single newline a hard break, so pasted multi-line text keeps the lines the user pasted.
- **Bug 11 — paste listener fires inside widget input fields** — same handler, same commit. `use-canvas-paste.ts` binds `paste` on `document` with no target check, so pasting inside any widget's editor/input ALSO spawned a stray note or bookmark next to it. Now bails on `e.defaultPrevented` (ProseMirror already handled it) or when the event target is editable — `isContentEditable`, or inside `input, textarea, select, [contenteditable='true'], .ProseMirror`.

- **Bugs 2 + 12 — caret couldn't be placed in a note; interaction model rebuilt** — the actual blocker was CSS, found only after reading `@xyflow/react/dist/style.css`: line 215 sets `user-select: none` on EVERY `.react-flow__node`. That inherits into the note's ProseMirror, and a `user-select: none` ancestor makes the browser drop click-to-place-caret and drag-to-select inside a `contenteditable` — `contenteditable` does not re-enable selection by itself. Programmatic `focus()` still worked (it sets a selection via JS, bypassing hit-testing), which is exactly why the earlier attempts looked like they should work and didn't. Fixed in `app/globals.css`: any `.ProseMirror`/`[contenteditable]`/`input`/`textarea` inside a node opts back into `user-select: text`.
  - **Then the model itself was replaced** (user's call — feature 2 pulled forward), because the old one was generating a new exception per bug. New model lives in **`lib/canvas/widget-interaction.ts`** as data, not branches: two axes — canvas `mode` (`grab` | `select`) × widget `phase` (`idle` | `selected` | `editing`) — resolved through one 6-cell table (`CHROME`) into a `WidgetChrome` record (`draggable`, `interactive`, `claimsDrag`, `claimsWheel`, `textSelectable`, `showResizeControls`, `cursor`). Class names come from `widgetChromeClassName` (flag→class tables), xyflow's per-mode props from `FLOW_PROPS_BY_MODE`, pane cursor from `CANVAS_CLASS_BY_MODE`. `widget-node.tsx` is now a thin renderer of that record — the nested-ternary className, the `isEntered` alias and the per-type carve-outs are gone. 30 unit tests in `tests/widget-interaction.test.ts` pin every cell.
  - **`ALWAYS_INTERACTIVE_WIDGET_TYPES` deleted.** It existed because interaction was gated by `pointer-events-none`, so any widget with a button/control needed an exemption. In `select` mode every widget body is live from the first click, so the exemption list has no reason to exist. What replaces it is one honestly-scoped flag, `TEXT_EDITING_WIDGET_TYPES` (just `markdown`): the only genuine ambiguity is _drag_ — inside text it must select characters, on a card it must reposition, and no heuristic separates those. Figma/Miro/tldraw all resolve it with double-click-to-edit, so that gate stays for text widgets only.
  - **New UI:** `CanvasModeToolbar` (left edge, mirrors the widget toolbar) switches grab/select; `CanvasModeProvider`/`useCanvasMode` carry the mode. **Grab is the default** (user's call — opening a canvas starts with looking around it, and a stray first drag should pan rather than marquee-select or nudge a widget). In `select`, left-drag on the pane marquee-selects (groundwork for feature 2's bulk ops), middle-drag pans, and xyflow's own `panActivationKeyCode: "Space"` gives hold-Space panning — no key handling of ours.
  - `markdown-widget.tsx` stopped restating `nodrag`/`nowheel`/cursor on its scroll container; those come from the card shell's chrome and apply to descendants.
  - Two mechanical defects fixed along the way, both still valid:
  1. **Resize controls stayed layered over the content while editing.** `NodeResizer` had `isVisible={selected}`, and entering a widget never clears `selected`. The resizer must be the LAST child in DOM order to be grabbable at all, so its transparent 10px edge bands and 22px corner squares (fixed screen size via `autoScale`) sat on top of the card — while typing in a 340px-wide note, a 10px frame of resize-drag targets covered the text, and any click near an edge started a resize instead of placing the caret. Now `isVisible={selected && !entered}`: resizing belongs to the selected state, typing to the entered state.
  2. **The entering gesture never reached the editor.** The card body is `pointer-events-none` until `entered` flips, so the double-click that enters is consumed by the gate — ProseMirror saw no click, got no selection, and the caret landed at the start of the document regardless of where the user aimed. `WidgetNode` now records that gesture's viewport coords as `enterPoint` on the chrome context, and `MarkdownWidget` replays it via `editor.view.posAtCoords()` + `commands.focus(pos)` (falling back to `"end"` when the point misses the text, e.g. card padding). That effect is ordered AFTER the `setEditable` effect deliberately — focusing a non-editable view puts the caret nowhere.
  - Also: double-click no longer sets `entered` on `alwaysInteractive` widgets (media/board/gallery/bookmark/project-doc/mail-summary). They're interactive from the first click, so entering bought nothing — and after fix 1 it would have actively cost them their resize controls, plus `nodrag` on the whole card removes the only remaining way to grab a headerless card and move it.

- **Bug 4 - end-to-end invitation flow** - before this, `inviteMemberAction` created an `invitation` row via `auth.api.createInvitation` and nothing else happened: no `sendInvitationEmail` callback configured, no accept page, no mail provider installed. Built the whole path:
  - **Mail transport** - `lib/email.ts`, one provider-agnostic `sendEmail()`. SMTP/nodemailer rather than an API provider BECAUSE this app has no custom domain: Resend (and every API provider) only delivers to arbitrary recipients from a DNS-verified domain, and `*.vercel.app` can't be verified since we don't control that zone - it would have worked for emailing ourselves and failed for every real invitee. SMTP with a real mailbox's app password sends to anyone today with no DNS. Swapping to Resend once a domain exists means reimplementing one function. With no SMTP env vars it no-ops and logs the link (same graceful degradation as `lib/rate-limit.ts`), so dev/CI need no secrets. Env: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `EMAIL_FROM`.
  - **Email content** - `lib/emails/invitation.ts`: absolute links off `BETTER_AUTH_URL`, html-escaped (a workspace name can't inject markup), always with a plain-text alternative, access shown in UI wording (`member` -> "View only") not internal role names.
  - **Delivery hook** - `sendInvitationEmail` on the organization plugin. Deliberately swallows send failures: a mail outage must not roll back a valid invitation, since the same link is available via Copy link.
  - **Accept page** - `app/accept-invitation/[id]/page.tsx`. Every case is an explicit state via `resolveInvitationState` (`lib/invitations.ts`, 8 unit tests): pending, not-found, wrong-account, expired, accepted, closed. It reads the invitation row directly instead of `auth.api.getInvitation`, which scopes lookups to the signed-in user's email and errors on mismatch - that made "clicking the link while signed into another account", the most likely confusion, indistinguishable from expired/cancelled. Reading the row lets the page name the exact invited address and offer a one-click `SwitchAccountButton` (sign out -> back to the same invitation).
  - **Auth round trip** - no session redirects to `/sign-in?callbackURL=<invite path>&invited=<email>`; sign-in previously hardcoded `callbackURL="/workspaces"` in BOTH its session redirect and `OAuthButtons`, so an invitee would have been silently dropped there and lost the invite. Google/GitHub create the account on first sign-in, so "has an account" and "doesn't" are one flow. `callbackURL` is attacker-supplied, so it goes through `safeInternalPath` (`lib/safe-path.ts`, 12 unit tests) rejecting absolute, protocol-relative, backslash and control-character targets - otherwise the invite link is an open redirect.
  - **After accepting** - joins the org, sets it active (so the user doesn't land in whatever org their session pointed at), then redirects to `/workspace/<slug>`. `listOrganizations` is membership-based, so the workspace appears in the list with no extra work.
  - **Copy link** - `CopyInviteLinkButton` in the pending-invites list: works with no SMTP configured, when mail lands in spam, or to paste into chat. Built from `window.location.origin` so it matches the host actually in use.

- **Bug 5 - toolbar not draggable on mobile** (`53a4072`) - sensor conflict, not missing touch support. `PointerSensor` AND `TouchSensor` were both registered, and since `pointerdown` fires before `touchstart`, PointerSensor always won on touch, so TouchSensor's activation delay never applied. PointerSensor then tried to activate after 4px of movement, which the toolbar's own vertical scrolling won every time. PointerSensor removed; mouse keeps a short distance (a click stays a click), touch uses press-and-hold with a movement tolerance - that tolerance is what keeps the toolbar scrollable, since a swipe passes it before the delay elapses. Buttons also opt out of the long-press selection callout, which hijacks the gesture on iOS. Separately: the buttons had NO `onClick` at all, so tapping did nothing on any device and dragging was the only way to add a widget. A tap now drops the widget in the middle of the current view.

## Architecture Decisions

- **Use the official `@tiptap/markdown`, not `tiptap-markdown`** — the community package returns an HTML string and overrides `setContent`/`insertContentAt` to parse markdown implicitly (the second with `inline: true`), which silently double-parses anything a caller pre-parsed and flattens block nodes. The official extension is version-locked to Tiptap, returns ProseMirror JSON, and only parses when a call passes `contentType: "markdown"` — explicit, single-pass, no trap.
- **Markdown paste needs a detector regardless of package** — `@tiptap/markdown` has NO paste handling: it parses only for explicit `contentType: "markdown"` callers, and ProseMirror's default paste path never passes that. `MarkdownPasteHandler` exists solely to decide when the clipboard's plain-text flavour is markdown source; parsing itself is entirely the official extension's.
- **Markdown source pasted onto the canvas is stored as `pendingMarkdown` and parsed by the note's own editor, never pre-parsed at the paste site** — the paste hook has no editor instance, so it cannot know which nodes are permitted; a doc built there can only ever be plain paragraphs. Same handoff shape as bookmark's `pendingUrl`.
- **Clipboard flavour arbitration for markdown paste** — real formatting tags in `text/html` mean ProseMirror's html path wins; a `<pre>`/`<code>`-only wrapper means the plain-text flavour is markdown source and gets parsed as such. Rationale: copying a fenced markdown block out of a chat or docs page is the most common way markdown source reaches these editors, and its only rich tag is the wrapper itself.
- **Document-level canvas listeners must check the event target** — the canvas paste hook is bound to `document`, so anything editable inside a widget would otherwise double-handle every paste. Guard on `defaultPrevented` plus an editable-target test.
- **Never resolve a Judge0 language by name PREFIX** — `"javascript".startsWith("java")`, so Java resolves to Node and Java source compiles as JavaScript, silently and always in that direction. Compare the family name (everything before the `(version)` suffix) for equality. Numeric ids stay un-hardcoded because they differ per instance, with the CE ids as a fallback only.
- **A separate browser window is a separate QueryClient** — `invalidateQueries` cannot cross documents, so anything the editor window changes reaches the canvas over a BroadcastChannel, posted only after the write lands and treated by the receiver as display state it never writes back. This is not a violation of the one-QueryClient-per-root rule; the rule is per document.
- **Generated-harness protocol lives in ONE exported function** (`harnessProtocolSpec`) read by both the model prompt and the parser, and pinned by a test. A sentinel or delimiter changed in only one of the two fails silently and looks like the model misbehaving.
- **Assisted-mode code execution embeds its test cases and reads no stdin** — one submission per run rather than one per case, because the free Judge0 tier is counted in submissions. Anything that would show an input box in that mode is a control with no effect.
- **Code execution runs on a self-hosted Judge0, not a hosted API** — every hosted free tier either requires a card or has closed to the public, and the one option that needed no account (Piston) downloads its runtimes at start-up, which this machine's Docker networking blocks. Judge0's image carries its compilers, so it needs no egress. Corollary: `isJudge0Configured()` must not require an API key, because the normal setup has none.
- **A provider abstraction earns its place only with a second provider in it** — the Judge0/Piston executor layer was written, worked, and was deleted the moment Piston was dropped rather than kept for a hypothetical third. Git history holds it.

- **Every notification row is written by `notify()` in `lib/notifications.ts`, and only from a server action that already resolved identity, org scope and its write check.** It is deliberately NOT in a `"use server"` file - exporting it there would make "notify arbitrary user ids" a client-callable endpoint.
- **Who gets notified is decided from the id-carrying `mention` node in stored JSON, never from `@name` text** - names are neither unique nor stable.
- **Notification dedupe is the unique `dedupe_key`, not the save-side diff.** The diff (`diffMentions` prev vs next, read only when the incoming doc mentions anyone) just avoids work; the constraint is what makes autosave bursts, the save retry and racing tabs safe on Neon HTTP, which has no transactions.
- **Notification queries are per-USER keys and must stay out of the localStorage persister** - they are static keys, so persisting them would hydrate one account's notifications into the next account on the same browser.
- **The public share page never receives mention data** - `getDocProjectByShareToken` runs every page through `redactMentions` (lib/mentions.ts), replacing each mention with plain `@teammate` text. Done server-side on purpose: the page JSON is serialized into the HTML payload, so hiding chips in the renderer would still ship names and user ids to anyone with the link (user decision 2026-09-24).
- **Every `<img>` of a user avatar needs `referrerPolicy="no-referrer"`** - Google avatars (`lh3.googleusercontent.com`) return `429` when the request carries our Referer and `200` without one (verified with curl 2026-09-24). Your own avatar looks fine only because the browser cached it; everyone else's shows the broken-image alt. Applies to the user menu, the notification bell and the `@` picker today, and to any avatar added later.
- **Canvas landing targets (`?focus=`, default landmark) are decided inside `handleFlowInit`, never in a mount effect** - the mount-effect version already lost a race with xyflow's own fitView once.
- **Strip canvas query params with `window.history.replaceState`, not `router.replace`** - the workspace route is force-dynamic, so a router navigation refetches the whole page payload (board, mail) just to drop a param.

- **Comment pins are not widgets and not xyflow nodes** - they live in `comment_threads` and render inside `<ViewportPortal>`. Widget rows need `canWriteWidgets` (view-only members could never comment) and anything in the nodes array flows through `useWidgetLayout`'s widget-save path, marquee select and Delete-key removal. `.react-flow__viewport` is `pointer-events: none`, which the portal inherits - pins opt back in with `pointer-events-auto`.
- **`canComment` includes `member`** - the first write a view-only invitee can make. It grants nothing else; `canWriteEntries`/`canWriteWidgets` are unchanged and tests pin that.
- **Comment bodies render through `CommentBody` (a small React renderer over the JSON), not a read-only editor and never an HTML string** - links only for http(s)/mailto.
- **Comment composer Enter-to-post lives in `editorProps.handleKeyDown` and checks `isSuggestionActive`** - direct editor props run BEFORE plugin key handlers, so without the check Enter would post instead of picking a person in the `@` list.

- **Notification email is an outbox, not a fire-and-forget send** - `after()` is best-effort (AGENTS §12); the `email_outbox` row + daily cron is the guarantee, and the unique `notification_id` means the notification's dedupe key also dedupes email.
- **Unsubscribe links authenticate nobody; the HMAC token can only turn one kind OFF for one user** - never add a token path that turns anything ON or reads anything else. Body link is a confirm page with a button (mail scanners prefetch GETs); only the RFC 8058 POST acts immediately.
- **Custom domain DNS trap (2026-09-24):** right after adding records, some resolvers (the user's carrier DNS, even a remote fetcher) served stale GitHub Pages IPs (`185.199.108-111.153`) for ~30 min - Namecheap's 30-min TTL on an earlier answer. Not a config error; check the TTL countdown before changing records again.
